# PPC engine swap — validation plan (Linux + GPU)

Validates `feature/ppc-icecube-submodule`: replacing the vendored PPC binary
with the `icecube/ppc` submodule (`bdaa599`) built at install time. The gate for
merging is **"ice output does not change"** plus **"multi-PMT works end to end."**

Run these on a Linux host with a CUDA toolchain. Each phase lists commands and
explicit pass criteria.

---

## Phase 0 — build & binary sanity

```bash
git checkout feature/ppc-icecube-submodule
git submodule update --init --recursive resources/PPC_executables/ppc-src
bash scripts/install_ppc.sh
```

Checks:
- `ls resources/PPC_executables/bin/` shows **`ppc_cpu`** and **`ppc_gpu`**.
- `file resources/PPC_executables/bin/ppc_*` — CPU is an ELF; GPU links CUDA.
- Multi-PMT support is compiled in:
  ```bash
  strings resources/PPC_executables/bin/ppc_gpu | grep -E "getPMT|HIT %d %d_%d"
  ```
  Expect both the `getPMT` symbol and the `HIT %d %d_%d ...` (per-PMT) format.
- Smoke run (no args prints usage, i.e. it loads):
  ```bash
  resources/PPC_executables/bin/ppc_cpu || true
  ```

**Pass:** both binaries build; GPU binary contains `getPMT` + the `dom_pmt` HIT
format; both start without a linker/loader error.

## Phase 2 — ice A/B regression (PRIMARY GATE)

Goal: prove the `bdaa599` engine reproduces `main`'s current ice light output.
Because PPC seeds its RNG from wall-clock time (not built with `DTMN`), compare
**ensembles/distributions**, not event-by-event.

Setup — identical events, two engines, one detector:
1. Fix the injection so both runs see the **same events**:
   `config.injection.LeptonInjector.simulation.random_state_seed = <fixed>` (or
   reuse a single committed `..._LI_output.h5`).
2. Detector: an **ice** geometry (`icecube.geo`), ice tables
   (`PPC_tables/south_pole/`). All modules legacy (`module_type == -1`) so the
   engine runs in non-multi-PMT mode.
3. Baseline run — `main`'s committed binary:
   ```bash
   git worktree add ../prom-main main
   # point PPC_EXE / ppc_exe at ../prom-main/resources/PPC_executables/PPC/ppc
   python examples/run_prometheus_sim.py ...   # -> baseline.parquet
   ```
4. Candidate run — this branch's built binary (`bin/ppc_cpu`), **same injection,
   same seed** → `candidate.parquet`.

Compare with `scripts/ab_compare_hits.py` (see below), split by event topology:

| Observable | Cascade (EMinus/Hadrons) | Track (MuMinus) |
|---|---|---|
| total PE / event (mean) | within ~1% | within ~2–3% (watch the `extr` term) |
| total PE / event (shape) | KS p > 0.01 | KS p > 0.01 |
| per-OM occupancy map | corr > 0.999 | corr > 0.99 |
| hit-time distribution | KS p > 0.01 | KS p > 0.01 |
| wavelength distribution | KS p > 0.01 (identical acceptance) | same |

**Pass:** cascades statistically indistinguishable; tracks within the small
tolerance. A cascade mismatch is a real regression — investigate before merge. A
small, energy-dependent **track-only** shift is expected (the bare-muon `extr`
light term differs from the committed-stock source; see the plan doc's physics
notes) — record its size but it is not a blocker if cascades match.

Run at two energies (e.g. 1 TeV and 1 PeV) so any energy-dependent `extr`
difference is visible.

## Phase 3 — multi-PMT end to end

Requires a multi-PMT detector **and** its sensor tables. The engine needs, for
each OM type used: `om.conf` + `om.map` (generated by Prometheus), the shared
`om.dirs` (now shipped), and **`om.wv_<omtype>.<pmttype>`** (+ optionally
`eff-f2k`). Missing `om.wv_` yields **zero hits silently**, so source it first.

- Reuse Pavel's `arca_water` set as the known-good example: it ships
  `om.dirs`, `om.wv_1.0`, `eff-f2k` for OM type 1. Point `ppctables` there and
  use a geometry whose modules are `module_type == 1`.
- Run a small sample (e.g. 100 events) through `bin/ppc_gpu`.

Checks:
```bash
grep -c "HIT" <ppc_output>           # nonzero -> light is produced
grep -m3 "HIT .* [0-9]_[0-9]" <ppc_output>   # dom_pmt (underscore) format present
```
Then in Python: `parse_ppc(out)` returns hits with `pmt_id is not None`, and
multiple distinct `pmt_id` values are exercised (for an mDOM-like type, up to its
PMT count).

**Pass:** nonzero hits; per-PMT (`dom_pmt`) output; `parse_ppc` yields integer
`pmt_id`s spanning more than one PMT; total light is physically sane (sum over
PMTs comparable to the single-PMT equivalent for the same geometry/energy).

## Phase 4 — CPU/GPU consistency

Same events + same tables through `bin/ppc_cpu` vs `bin/ppc_gpu` (both are
`bdaa599`, so physics should match within RNG fluctuation).

**Pass:** ensemble distributions (total PE, timing) statistically consistent.
This isolates a GPU-build problem from a physics change.

## Appendix — `om.wv_` sourcing (blocks Phase 3 for new module types)

`om.wv_<omtype>.<pmttype>` is the sensor's wavelength→effective-area (QE×area)
curve — real per-sensor physics, one file per multi-PMT module type. Today only
`arca_water/om.wv_1.0` exists. To support another module type, produce its
`om.wv_` from that sensor's spectral QE/area (ideally derived from wherever
Prometheus already stores module efficiency), named by the `module_type` in
`om.conf` and the PMT type in `eff-f2k` (default `0`). Until then, multi-PMT
runs for that type emit no light.
